# Contributing and Architecture

Prosa-Kobo is a Rust service built on [axum](https://github.com/tokio-rs/axum)
and [sqlx](https://github.com/launchbadge/sqlx), keeping its own state in
SQLite. Issues and pull requests are both welcome. See
[CONTRIBUTING.md](https://github.com/tiago-cos/prosa-kobo/blob/master/.github/CONTRIBUTING.md)
for the short version of what a pull request needs.

## Building and running

```bash
git clone https://github.com/tiago-cos/prosa-kobo.git
cd prosa-kobo
cargo run
```

It needs a running Prosa to start. Settings go in
`src/config/configuration.toml`; copy `src/config/example.toml`, a complete one
at default values, to start from it. Both that file and the database, under
`persistence/`, are git-ignored. See [Configuration](Configuration) for the
rest.

## Running the tests

```bash
cargo test
```

Unit tests sit beside the code they cover. Integration tests live in `tests/`,
one file per domain. They build the real router and drive it in process, with
`MockProsaClient` standing in for Prosa, so they need neither Prosa nor a
listening socket. `tests/common/mod.rs` holds the harness, and `tests/fixtures/`
the books they use.

The database pool, the Prosa client and the KEPUB cache are static, so the tests
in a binary share them. The harness hands them to one test at a time and empties
the database, the mock and the cache first, so each test still starts clean.

### Keeping the mock honest

`tests/prosa_contract.rs` runs every scenario twice: once against the mock and
once against a real Prosa. The real half is skipped by default. Run both against
a Prosa started with an admin key, preferably the `tsousa28/prosa:latest` image,
whenever the mock or Prosa changes:

```bash
PROSA_URL=http://127.0.0.1:5000 PROSA_ADMIN_KEY=admin_key cargo test --test prosa_contract -- --include-ignored
```

A scenario that passes against Prosa but fails on the mock is drift to fix in
the mock, not in the scenario.

### Testing on a Kobo

`examples/device_test` walks a tester through every feature on a real Kobo. It
acts in Prosa as another device would, tells the tester what to do on the Kobo,
and checks that each change arrived on the other side, down to the characters a
highlight covers. It needs Prosa and Prosa-Kobo running, and a Kobo that can
reach Prosa-Kobo:

```bash
cargo run --example device_test -- --kobo-address 192.168.1.20:5001
cargo run --example device_test -- --only annotations,reading
cargo run --example device_test -- --list
```

- **The account.** The first run registers a Prosa user of its own, links a
  device to it, and prints the `api_endpoint` to set on the Kobo. Everything is
  kept in `.device-test/`, which is git-ignored and holds credentials, so later
  runs reuse it. Your own library is never touched. `--reset` empties the test
  library, unlinks the Kobo and forgets the account.
- **The suite's own key.** It acts in Prosa with a second key, because Prosa's
  sync leaves out what a key did itself.
- **Sections.** Each section starts by replacing the test library with the books
  it needs, so any section can run alone.
- **Books.** The books are generated by `books.rs`, not downloaded. `epub.rs`
  writes them and resolves Prosa locations against them, counting as `kepub-rs`
  does. The unit tests beside `books.rs` run under `cargo test` and prove every
  phrase a step names survives the trip to a Kobo position and back.
- **Results.** Any step can be skipped or failed with a note. The summary is
  saved to `.device-test/report.md`.

Prosa's address is read from `PROSA_URL`, Prosa-Kobo's from `MIDDLEWARE_URL`,
and an admin key, when registration needs one, from `PROSA_ADMIN_KEY`. When a
behaviour the Kobo can see is added or changed, add or update the step that
exercises it.

## How the code is laid out

```
src/
├── main.rs          entrypoint and the migration CLI
├── lib.rs           the crate root, so tests/ can link against it
├── config/          configuration loading
├── database/        connection setup, the static pool and migrations
├── client/          the Prosa client
└── app/             the application, by domain
```

`src/app/` is organised **by domain first, then by layer**. Most domains
(`annotations`, `books`, `covers`, `devices`, `metadata`, `shelves`, `state`,
`sync` and the rest) are a directory with the same files:

| File | Holds |
|---|---|
| `routes.rs` | Route definitions |
| `handlers.rs` | Request handling: extract, call one service function, shape the response |
| `service.rs` | Business logic, including loops over items and work spanning domains |
| `data.rs` | Database access |
| `models.rs` | The structs and errors the domain is made of |
| `mod.rs` | Module declarations |

`kepub/` has no endpoints, only `models.rs` and `service.rs`: EPUB to KEPUB
conversion, the converted-book cache, and translation between Prosa's locations
and the Kobo's positions.

`src/client/` holds the Prosa client. `ProsaApi` is an async trait mirroring
Prosa's endpoints, with one real implementation and `MockProsaClient` for tests.
Services take a `&dyn ProsaApi`, so their unit tests can hand them a mock of
their own.

### How a Kobo request is handled

A device's endpoint ends in a secret lookup key, so every request it makes
arrives with the key as its first path segment. Middleware strips the key before
routing, so routes and handlers never see it, and resolves it to the Prosa API
key the request is translated with.

Requests under `/api/v3/content` are the exception. The Kobo builds them from an
address it keeps only the origin of, so they arrive with no key. They are matched
on the `x-kobo-deviceid` header instead, which keyed requests record as they
pass.

Every URL the Kobo is handed is built by `app::device_url`, from
`[server.public]` when set and otherwise from the host the Kobo addressed.

### Reading state

`device_states` records, for each device and book, the reading status and
position the device holds. That is what decides how a reading state is dated
when the Kobo opens a book, and whether sync sends it at all, so that a position
changed elsewhere is offered rather than forced. `CLAUDE.md` in the repository
has the full rules. Take care when changing them, and run the reading section of
the device test afterwards.

## Conventions worth knowing before you change something

**Data functions take an executor, not the pool.** Pass `pool()` for a
standalone query, or `&mut *tx` to join a transaction in flight.

**Errors are mapped, not panicked.** Data functions return a `Result`. Each
domain maps sqlx errors to its own error in `models.rs`, and hands anything it
cannot map to `error::unmapped`, which logs it and answers 500.

**Pure mappings live on the Kobo models**, as `From` impls or constructors. A
service only adds what needs Prosa or the KEPUB, such as translating a position.

**Every timestamp the Kobo is sent goes through `app::kobo_time`**, which writes
Kobo's format with seven fractional digits.

**Never edit a migration that exists.** sqlx records each one's checksum, and a
changed migration stops Prosa-Kobo from starting. Add a new one instead.

**Every migration needs both directions.** `NNNN_description.up.sql` and
`NNNN_description.down.sql`, so downgrades stay possible.

## The OpenAPI spec

`openapi/` is the reference for Prosa-Kobo's own API: the health check and the
device management endpoints. The Kobo-facing endpoints imitate Kobo's and are not part of it.

- `openapi/openapi.yaml`: the root document
- `openapi/paths/`: one file per path, in directories mirroring the URL
- `openapi/components/`: schemas, responses and parameters shared between them

Check and build it with the Redocly CLI:

```bash
npx @redocly/cli lint openapi/openapi.yaml
npx @redocly/cli build-docs openapi/openapi.yaml --output=docs/index.html
```

The published reference at
[tiago-cos.github.io/prosa-kobo](https://tiago-cos.github.io/prosa-kobo) is
built by the **Deploy API Docs** workflow, which is dispatched by hand.
